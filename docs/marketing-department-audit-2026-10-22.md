# 弋阳龟峰颐养中心管理平台——市场部功能检查与优化报告

检查日期：2026-10-22  
检查范围：市场部前端路由、菜单、API、数据库迁移、权限、核心业务服务、运行中的本地测试环境  
测试身份：`MARKETING_EMPLOYEE`、`MARKETING_MINISTER`、`FINANCE_EMPLOYEE`（均为本地演示账号）

## 一、结论摘要

系统已经具备“咨询线索 → 跟进/回访 → 床位预订 → 评估/入住办理 → 合同签署 → 签后回访 → 经营报表”的主体骨架，线索、合同、入住、床位、评估、账单、医护档案之间也有代码级联动。实际 API 测试确认线索新增、编辑、查询、刷新后持久化、回访计划创建与执行、删除清理均可用；浏览器测试确认核心页面可以打开，普通市场员工对主管级动作会被后端拒绝。

但目前还不能评价为“普通市场员工全天使用很方便”：最关键的缺口是没有真正的“客户预约参观/到访结果”业务对象；重复客户可以被连续录入；线索表单字段多且渠道大量自由输入；部分列表存在全量扫描和逐行请求风险。此次已完成低风险修复：隐藏普通员工无权执行的分配、删除、最终签署和审批按钮，修正误导性的筛选与短信设置文案，实现真实 CSV 导出，并补上线索姓名服务端校验。

## 二、现有业务与数据关系

### 2.1 市场员工日常工作链路

1. 工作台查看待办、今日跟进、逾期客户和经营摘要。
2. 在线索池登记咨询人/老人、联系方式、来源、意向和负责人。
3. 建立回访计划，填写执行记录和下次跟进时间。
4. 高意向客户转床位预订、锁床、评估和入住办理。
5. 建立合同，上传附件，完成评估、入住和主管最终签署。
6. 入住后、试住和退住回访；主管查看渠道、转化、人员业绩和经营快照。

### 2.2 主要数据表

`crm_lead`、`crm_callback_plan`、`crm_contract`、`crm_contract_attachment`、`crm_sms_task`、`crm_marketing_plan`、`crm_lead_assign_log`、`crm_stage_transition_log`、`crm_contract_workflow_log`、`crm_sales_report_snapshot`，并关联长者档案、入住、评估、床位、账单和健康档案数据。

### 2.3 跨部门衔接

| 衔接方向 | 当前实现 | 评价 |
|---|---|---|
| 市场 → 护理/医务 | 合同办理读取/更新评估记录，最终签署联动健康与医护准备数据 | 有代码实现；本次未在浏览器完成跨部门终态签署，标记部分未验证 |
| 市场 → 入住/床位 | 合同与线索可创建或更新入住记录，最终签署执行床位占用 | 主链完整；禁止用生产数据实测终态，未做破坏性验证 |
| 市场 → 财务 | 合同签署联动账单月份、押金/收费准备；财务角色可读合同 | 有实现；财务读取已实测，账单生成未做终态实测 |
| 医护 → 市场 | 存在“外来就医转线索”场景和来源统计 | 页面存在；缺少真实医护转入样本，未验证数据自动产生 |
| 市场内部 | 分配日志、阶段日志、合同流程日志、回访计划与经营快照 | 基础追溯能力完整 |

## 四、发现的问题

| 问题位置 | 复现步骤 | 实际表现 | 期望表现 | 原因 | 严重程度 | 修复方案/状态 |
|---|---|---|---|---|---|---|
| 新客户登记 | 连续提交相同老人姓名和电话 | 两次均成功，查询得到 2 条 | 提示疑似重复，并允许主管确认合并/继续 | 服务直接插入，无重复匹配策略 | P1 | 未直接改；需先确定“同一联系人对应多位老人”等规则 |
| 预约参观 | 查找市场菜单和 API | 只有床位预订，无潜客参观预约/到访结果 | 可排期、提醒、签到、记录参观结果并回到跟进池 | 缺少独立业务对象和流程 | P1 | 未改；建议第一优先级补齐 |
| 线索列表性能 | 大数据量打开线索/回访页 | 存在多页全量扫描，并可能逐行请求回访计划 | 列表单次分页查询，摘要和回访状态由聚合接口返回 | 前端聚合过多 | P1 | 未改；建议后端增加汇总/批量接口 |
| 合同可见范围 | 普通市场员工查询合同 | 可看到机构内多份合同，而线索列表按本人归属隔离 | 明确“团队共享”或“本人/协作人可见”口径 | 合同与线索采用不同数据范围 | P1 | 未改；先由主管确认数据权限 |
| 线索/合同主管动作 | 普通员工打开页面并点击分配、删除、最终签署/审批 | 原页面显示按钮，后端返回 403 | 无权限动作不显示，并解释由主管处理 | 前端只按路由权限判断或未判断角色 | P2 | 已修复并浏览器验证 |
| 线索请求校验 | 提交没有任何姓名字段的请求 | 可生成“未命名线索” | 服务端拒绝并给出可理解提示 | `@Valid` 存在但 DTO 无约束 | P2 | 已补兼容三种姓名字段的服务端校验与测试 |
| 续签导出 | 点击“导出” | 原来只提示“任务已提交”，没有文件 | 下载当前页 CSV 或明确后台任务位置 | 按钮为占位实现 | P2 | 已实现真实 CSV；浏览器下载内容已验证 |
| 到期提醒设置 | 点击“到期提醒设置” | 只展示短信任务记录，不能设置规则 | 名称与实际功能一致，或实现规则配置 | 文案与功能不符 | P2 | 已改名“短信任务记录”；规则配置仍缺失 |
| 不存在记录的写操作 | 主管对不存在 ID 执行分配等 | 可能返回 HTTP 200、`data=null` | 404 或明确业务错误 | 服务以 `null` 表示未找到，控制器仍 `Result.ok` | P2 | 未改；建议统一异常语义后再改调用方 |
| 线索表单 | 新增咨询 | 字段多、来源/渠道自由输入、咨询人与老人信息重复 | 首屏只保留必填与高频字段，来源用配置项，更多信息折叠 | 页面一次承载全部阶段信息 | P2 | 未做大改；涉及数据字典和业务规则 |
| 默认筛选提示 | 打开全部线索 | 没有手动筛选也显示“启用 1 个筛选条件” | 仅统计用户输入的筛选 | 把默认阶段页签计入筛选数 | P3 | 已修复 |
| 旧页/无入口组件 | 代码检索 | 隐藏旧 CRM 页及无路由组件继续存在 | 兼容期结束后删除，避免双实现漂移 | 历史迁移保留 | P3 | 未删除，避免破坏旧书签/外链 |

| 原有操作流程 | 存在的问题 | 建议的新流程 | 预计减少步骤 | 是否已实现 |

## 八、尚未解决的问题与下一步

1. **P1 预约参观缺失**：建议新增 `crm_visit_appointment`（线索、预约时间、陪同人、到访状态、结果、取消原因、下次跟进），在线索页一键创建，并进入工作台今日到访。该调整涉及数据库、API、日历和统计，先评审后实施。
2. **P1 重复客户识别**：先确定规则。建议同机构按标准化手机号 + 老人姓名精确提示，再辅以联系人手机号/证件号模糊候选；默认“提示不阻断”，只有证件号完全相同才阻断。
3. **P1 数据范围**：确认普通市场员工是否能看全机构合同。如果不是，应由后端按负责人/协作人过滤，不能只做前端隐藏。
4. **P1/P2 性能**：把列表摘要、回访计划状态和过期计算下沉到批量/聚合 API，避免前端全量翻页和 N+1 请求；用 1 万条线索压测。
5. **P2 表单简化**：把首访登记与后续完善拆成渐进式表单，渠道字段改用统一字典；不能直接改数据库枚举，以免历史报表断裂。
6. **P2 API 语义**：统一不存在/无权记录的 404/403 处理，并补控制器回归测试。
7. **P2 提醒规则**：续签短信目前有任务记录但无可配置提前天数、模板和发送时段。
8. **跨部门终态验证**：在独立测试库创建完整长者，执行评估、入住、锁床、签署、账单和医护记录核对；本次为避免污染真实/演示业务数据没有执行。
