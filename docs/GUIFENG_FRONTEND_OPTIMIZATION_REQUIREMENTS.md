# 弋阳龟峰颐养中心智慧管理平台前端改造需求清单

> 目标：保留现有系统与业务 URL，以最小改动完成“统一工作台、岗位化菜单、长者 360、协同闭环”。本文基于当前仓库代码整理，不以方案中的示意数据代替真实接口。

## 1. 范围与实施原则

### 1.1 本次范围

- P0：统一员工入口、六部门岗位菜单、护理高频任务体验、重复入口收口。
- P1：个人待办聚合、长者 360、入住等跨部门流程、移动端高频操作。
- P2：院长经营分析、部门质量分析、风险预警和智能辅助。

### 1.2 状态定义

| 标记 | 含义 | 开发动作 |
| --- | --- | --- |
| 复用 | 仓库已有页面和接口 | 不重写，只补入口、文案或验收 |
| 前端调整 | 接口已具备，页面组织仍需优化 | 修改现有组件、路由或菜单 |
| 后端前置 | 现有接口无法保证口径或权限 | 后端完成后再接入，不在前端推算 |

### 1.3 不变约束

- 保留现有业务路由；旧入口使用隐藏重定向兼容，不批量修改 URL。
- 菜单隐藏不是权限控制。菜单、搜索、快捷入口和直接 URL 必须统一调用现有路由权限模型。
- `/workbench/todo` 只聚合来源任务和导航，业务状态仍由来源模块维护。
- 不用部门汇总冒充“我的任务”或“我的业绩”；缺少个人口径时显示 `--` 和数据说明。
- 医疗、财务、账号权限等敏感操作保留复核、原单关联、审计和职责分离。
- 不删除历史页面或数据，不新增仅为展示而存在的接口。

## 3. 统一工作台

### 3.1 页面结构

`/workbench/overview` 固定为五个区域：岗位说明、今日优先事项、风险提醒、常用操作、最近处理。部门差异通过现有工作台适配器提供，不新增六套首页。

| 部门 | 复用数据源 | 员工口径 | 部长口径 | 尚缺能力 |
| --- | --- | --- | --- | --- |
| 护理 | `/api/care/tasks/summary`、`/api/care/tasks/page` | 当前员工今日任务 | 部门任务、待分配、风险 | 后端强制本人数据范围；人员执行聚合 |
| 医务 | `/api/health/medication/registration/page` | 本人用药留痕；其余缺口显示 `--` | `/api/medical-care/workbench/summary` 与统一任务 | 本人巡诊、医嘱和用药待办接口 |
| 财务 | `/api/finance/workbench/overview` | 明确标注机构当班口径 | 审批、欠费、异常、月结 | 本人收款、退款、票据和最近操作 |
| 后勤 | `/api/logistics/workbench/summary` | 明确标注机构当班口径 | 逾期、库存、采购、设备 | 按责任人和工种汇总 |
| 行政人事 | `/api/admin/hr/workbench/summary` | 本人考勤、本人信息、授权提醒 | 审批、异常、合同、培训、档案 | 本人经办事项汇总 |
| 市场 | `/api/marketing/report/workbench-summary` | 明确标注机构客户池口径 | 逾期、高意向、待签约、成交 | 按销售负责人安全过滤 |

### 3.2 通用验收

- 加载、空数据、无权限和接口错误四种状态有不同提示。
- 缺失值显示 `--`，不显示 `0` 或伪造示例。
- 卡片及快捷入口在渲染前执行路由权限检查。
- 状态不只依赖颜色，必须同时有文字或图标。
- 1280px 桌面端无横向滚动；高频操作在手机和平板可完成。

## 4. 六部门逐页需求

### 4.1 护理部

| 项目 | 要求 |
| --- | --- |
| 入口 | `/care/home` 为部门运行视图；员工默认仍为 `/workbench/overview` |
| 高频页 | `/care/today` 按紧急、超时、执行时间排序，支持待执行、执行中、待复核、异常筛选 |
| 单页闭环 | 在任务详情内完成要求查看、执行确认、必要记录、异常反馈，避免跳转到多个表单 |
| 复用接口 | `/api/care/tasks/summary`、`/api/care/tasks/page`、`/api/care/tasks/execute`、`/api/care/tasks/review`、`/api/care/tasks/exception/resolve` |
| 复用页面 | `/care/service/nursing-records`、`/medical-care/handovers`、`/medical-care/care-task-board`、护理排班和护理质量 |
| 员工权限 | 只处理本人或授权班组任务；不得分配、批量复核或查看部门绩效 |
| 部长权限 | 可分配、复核、查看待分配缺口、排班和质量；不可用任务预览推算个人绩效 |
| 后端前置 | 普通员工查询由服务端绑定登录身份，禁止通过改 `staffId` 查询他人任务 |

验收：护理员登录后首屏能看到当前班次重点；从任务列表到完成记录不超过一个详情页；异常必须填写处置结果并进入交接轨迹。

### 4.2 医务部

| 项目 | 要求 |
| --- | --- |
| 医生入口 | `/medical-care/rounds`、`/medical-care/orders` |
| 执行入口 | `/medical-care/order-executions`、`/medical-care/medication-registration` |
| 药事入口 | `/medical-care/pharmacy` |
| 部长视图 | `/medical-care/center`、`/medical-care/unified-task-center` |
| 安全要求 | 开立、执行、停止、复核按操作权限分离；记录操作者、时间、结果和复核人 |
| 告警要求 | 急救和危急告警优先于普通待办，并展示机构应急处置说明 |
| 后端前置 | 巡诊、医嘱、用药任务必须支持当前登录责任人范围；未完成前不得展示为“我的” |

验收：医生、执行人员和药事人员菜单不同；护理人员可执行授权医嘱但不能开立医嘱；急救告警在所有普通任务之前展示。

### 4.3 财务部

| 项目 | 要求 |
| --- | --- |
| 主入口 | `/finance/payments/cashier-desk` 集中账单查询、收款、凭证和支付结果 |
| 次级入口 | `/finance/payments/register` 保留收费登记，但菜单不与收银台并列为两个主入口 |
| 员工视图 | 收款、流水、票据、退款申请、日结交班 |
| 部长视图 | 费用审批、欠费、对账异常、退住审核、月结和经营分析 |

| 后端前置 | 提供按登录收银员过滤的今日操作与交班口径 |

验收：正常收费不重复录入长者和金额；重复提交不会产生第二笔流水；退款必须关联原流水且经办人不能审批本人申请。

## 5. 长者 360

### 5.1 页面组成

| 区域 | 内容 | 默认可见岗位 |
| --- | --- | --- |
| 基本与入住 | 身份、床位、入住状态、紧急联系人 | 业务需要相关岗位 |
| 护理服务 | 护理等级、计划、记录、异常 | 护理、医务、院长 |
| 健康医疗 | 健康档案、风险、医嘱、用药 | 医务、授权护理、院长 |
| 财务账户 | 账单、押金、预存余额、缴费状态 | 财务、院长；其他岗位仅显示必要状态 |
| 服务事件 | 报修、外出就医、投诉和处置 | 相关责任部门 |
| 流程轨迹 | 入住、转床、退住、审批、交接 | 参与部门及院长 |

### 5.2 实施要求

- 复用 `/api/elder/{id}`、护理档案和现有 `/api/medical-care/resident-360/{id}` 聚合能力。
- 路由必须携带稳定长者 ID；姓名只用于显示，不作为查询键。
- 卡片只展示摘要，修改操作进入所属业务单据，避免在聚合页复制业务表单。
- 后端按字段和业务域裁剪响应；不得只依赖前端隐藏医疗或财务字段。
- 每个数据块显示更新时间和来源模块；失败时局部降级，不拖垮整页。

验收：护理员无法读取完整账务和病历；收银员无法读取完整病历；单个接口失败时其他区域仍可使用；所有修改可回到来源记录和审计日志。

## 6. 跨部门协同

### 6.1 入住流程

| 阶段 | 责任部门 | 业务结果 | 建议并行关系 |
| --- | --- | --- | --- |
| 意向确认与发起 | 市场 | 建立入住流程实例 | 起点 |
| 护理与健康评估 | 护理、医务 | 评估结果与风险 | 可并行 |
| 床位与房间准备 | 后勤 | 床位确认、房间就绪 | 可与评估并行 |
| 合同与费用 | 市场、财务 | 合同签署、费用审核、缴费 | 依赖必要评估与床位确认 |
| 接收与服务计划 | 护理、医务 | 接收确认、护理和医疗计划 | 依赖签约与缴费规则 |
| 完成入住 | 系统 | 档案、床位、账单、任务状态一致 | 所有必需节点完成 |

### 6.2 统一流程规则

- 流程实例有唯一业务 ID；子任务保存来源类型、来源单号、责任部门、责任人和截止时间。
- 状态至少包括待处理、处理中、待复核、已完成、已退回、异常、已取消。
- 子任务完成由来源业务回写，聚合待办不能独立改成已完成。
- 退回、超时、改派、取消和重开均保留操作者、时间、原因和前后状态。
- 通知按普通、临期、超时、紧急分级；通知失败不影响业务事务，但必须可补发和查询。
- 入住完成使用服务端事务或可重试编排，避免档案、床位和账单部分成功。

同一机制后续复用于退住结算、健康异常、维修、费用审批和员工入离职，不为每个流程另建一套状态模型。

## 7. 权限与审计验收矩阵

| 场景 | 员工 | 部长 | 院长 | 系统管理员 |
| --- | --- | --- | --- | --- |
| 本人工作台 | 可用 | 可用 | 使用经营总览 | 使用系统治理 |
| 部门汇总 | 默认不可 | 本部门 | 跨部门经营视图 | 默认不可见业务数据 |
| 任务分配 | 默认不可 | 本部门 | 监督下钻 | 不因管理员身份自动获得业务权限 |
| 业务审批 | 无审批权 | 授权范围 | 授权范围 | 仅配置权限，不默认代办 |
| 敏感字段 | 最小必要 | 授权范围 | 决策必要摘要 | 配置可见不等于数据可见 |
| 权限配置 | 不可 | 不可 | 不可 | 可用 |

必须验证：菜单不可见、搜索无结果、快捷入口不渲染、直接 URL 返回 403、接口返回 403，五个入口的结果一致。

## 9. 自动化与上线验收

### 9.1 必跑检查

在 `admin-web` 执行：

```bash
npm run test:unit
npm run check:navigation
npm run build
```

同时执行仓库已有 RBAC 回归，至少覆盖六部门员工、六部门部长、院长、系统管理员及跨部门越权。

### 9.2 真实用户任务

| 任务 | 通过条件 |
| --- | --- |
| 护理员完成班次任务 | 首页直接可见；同一详情闭环；异常进入交接 |
| 医护执行医嘱 | 只能执行授权医嘱；身份、时间、结果和复核完整 |
| 收银员完成收费 | 账单进入收款；不重复录入；重复提交不重复记账 |
| 维修员处理工单 | 手机完成接单到完工；状态顺序合法 |
| HR 办理入职 | 清单责任明确；账号、合同、培训无漏项 |
| 市场完成回访 | 同页记录沟通和下次联系；逾期状态自动更新 |
| 部长追踪事项 | 可按责任人、状态、时间和超时筛选 |
| 跨部门办理入住 | 能看责任部门、当前节点、阻塞原因和完整轨迹 |

上线门槛：权限回归无越权、财务幂等测试通过、关键流程不存在部分成功、真实员工完成上述任务后确认可用。

## 10. 明确不做

- 不重建六套独立员工首页。
- 不批量改写现有业务 URL。
- 不把统一待办建设成第二套业务状态库。
- 不用前端本地过滤代替服务端数据权限。
- 不为尚未确认的到访、渠道或个人绩效能力预建接口。
- 不在数据口径和闭环机制未稳定前增加 AI 自动决策。
