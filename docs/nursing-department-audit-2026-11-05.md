# 弋阳龟峰颐养中心管理平台——护理部全面功能检查与优化报告

检查日期：2026-11-05  
检查范围：护理工作台、今日任务、任务执行与派发、护理记录、服务计划、护理等级、预约、排班、交接班、异常处理、统计报表、角色权限及护理收费联动。  
检查方式：代码与接口审查、角色权限回归、H2 隔离环境页面走查、前端类型检查与生产构建、后端针对性测试。未向现有业务库提交护理执行记录。

## 一、结论摘要

系统已经具备护理业务的主要页面和基础数据链路，但检查前存在三个会直接影响一线使用或数据安全的问题：护理任务接口角色边界过宽、一线护理员没有可用的任务执行入口、任务重复执行可能造成重复日志或重复扣费。本轮已经以低风险方式修复，并补充自动化回归。

当前可支持“部长派发—护理员查看本人任务—扫码核对—执行落账—记录查询”的最小闭环。距离正式成为稳定的护理生产系统，仍需优先补齐交接班不可篡改、异常事件闭环、计划版本追溯和跨组织人员校验。

综合判断：**可进入受控试运行，不建议在未完成 P1 项前作为唯一护理记录载体。**

## 三、已修复问题

### P0/P1 安全与数据正确性

| 问题 | 复现/影响 | 根因 | 修复结果 |
| --- | --- | --- | --- |
| 非护理/医务员工可访问护理 API | 普通员工令牌可请求 `/api/care/**` 或 `/api/nursing/**` | 全局安全配置未给护理路径设置专属角色边界 | 两组路径限制为医务、护理、院长和管理员角色；增加 403 回归测试 |
| 班次模板批量保存缺少细粒度权限 | 有护理域访问权的低权限用户可能修改班次模板 | `batch-save` 漏加 `@PreAuthorize` | 限制为护理部长、院长及管理员 |
| 客户端可伪造任务执行人 | 请求可传任意 `staffId` | 控制器信任客户端字段 | 服务端强制使用当前登录员工 ID |
| 护理员可执行已分配给他人的任务 | 已派发任务仍可被其他账号完成 | 执行服务未校验分配关系 | 非本人任务直接拒绝，必须先由管理者改派 |
| 重复执行可能重复写日志/扣费 | 双击或并发请求可能同时通过 DONE 检查 | 先读后写，无条件更新 | 用条件更新原子认领任务；未认领成功时按已完成返回，不再写后续流水 |
| 同一任务可能重复扣老人账户 | 重复调用收费链路会再次扣款 | 收费流水没有业务幂等检查 | 账户锁内按 `TASK + taskDailyId` 检查既有流水后再扣费 |

### P1/P2 可用性

| 问题 | 影响 | 修复结果 |
| --- | --- | --- |
| 今日任务没有执行按钮 | 一线护理员只能看任务，无法完成核心工作 | 新增执行入口和确认弹窗，复用现有执行 API |
| 执行前缺少身份核对 | 容易选错长者或床位 | 弹窗展示长者、房间、任务；床位二维码必填，并给出明确警告 |
| 护理员看到派发、评价等管理控件 | 容易误触且与权限不一致 | 按角色隐藏新增/派发、护理员筛选、派发和评价操作 |
| 护理员护理记录页面访问 403 | 菜单与后端权限不一致 | 允许护理员查询，但服务端强制限定为本人记录 |
| 强制改派默认开启 | 管理者可能无提示抢走已接任务 | 单个与批量派发默认关闭 `force` |
| 加载失败保留旧任务 | 护理员可能把过期数据误认为今天任务 | 失败时清空任务和指标，并显示错误信息 |
| 执行日志失败显示“暂无数据” | 把系统故障误判为没有记录 | 区分加载错误与空数据 |

## 四、仍需处理的问题与风险分级

### P1：上线前优先

1. **交接班记录缺少确认后不可变规则。** 当前更新、删除的所有权与状态约束不足。建议采用“草稿可编辑、本人提交、接班人确认、确认后只允许追加更正记录”的模型，不应直接覆盖原文。
2. **异常处置不是完整事件闭环。** 需要事件等级、发现人、长者、时间、现场处置、通知对象、责任人、时限、复核、结案与复盘；高等级事件应联动医务和管理层。
3. **服务计划缺少可审计版本。** 护理等级、项目、频次变化应生成新版本和生效时间，历史任务必须能关联当时版本。
4. **跨组织/部门人员校验不足。** 派发、交接、评价等写操作应验证目标员工属于当前机构且具备相应岗位。
5. **任务状态不足。** 目前核心状态以 `PENDING/DONE/EXCEPTION` 为主，无法准确表达进行中、延迟、拒绝、取消、补录和更正。

### P2：稳定性与效率

1. 护理记录先加载全部日志和预约再内存分页，数据增长后会变慢，应改为数据库分页或统一查询视图。
2. 今日任务的模板、员工等信息存在逐条查询，长列表会出现 N+1 查询，应批量加载。
3. 两名部长同时派发同一未分配任务时仍可能竞争，应把“未分配/原负责人”写进条件更新。
4. 收费幂等目前是应用层检查；生产环境建议增加数据库唯一约束，覆盖多实例并发与异常重试。
5. 强制生成每日任务的替换/去重语义需要在生产数据库上验证，避免重复生成。
6. 自定义任务每次创建禁用模板会积累配置垃圾，建议把临时任务与模板分离。

### P3：体验改进

1. 护理员移动端应提供更大的扫码与完成按钮、常用备注快捷项、离线/弱网草稿和未保存提醒。
2. 护理部长需要统一的待派发、逾期、异常、交接未确认看板，减少跨页跳转。
3. 院长视角应突出趋势、异常等级、责任部门和闭环时效，不宜直接堆叠明细表。
4. 生命体征和护理质量入口建议从今日任务或长者 360 档案直接深链。

## 五、角色验收结论

### 一线护理员

核心路径已能闭环：登录后看到本人任务，管理按钮被隐藏，选择任务后核对长者/房间/任务，扫描床位二维码并提交；后端记录真实登录人，拒绝执行他人已分配任务。护理记录也只返回本人数据。

结论：**基础任务执行可试运行**。弱网、移动端真机、异常上报和事后更正仍需专项验收。

### 护理部长

可以查看全员任务、派发、评价、处理任务异常、配置班次和查看报表。默认不再强制抢占任务。

结论：**日常派发与督办基本可用**。交接班不可变、并发派发和完整异常闭环未解决前，需保留线下复核机制。

### 院长/管理层

可以通过护理首页查看任务、风险和运营入口，角色权限可覆盖护理域。

结论：**可用于辅助管理，不宜作为唯一合规审计依据**，原因是计划版本、交接签名更正链和异常闭环尚不完整。

## 八、后续优先级 Top 10

1. 交接班所有权、确认签名、不可变与追加更正链。
2. 建立护理异常事件的分级、通知、处置、复核、结案和复盘闭环。
3. 为服务计划增加版本号、生效区间和历史任务关联。
4. 扩展任务状态与补录/更正流程，禁止直接覆盖原始执行事实。
5. 所有派发、交接、评价写接口增加机构与岗位归属校验。
6. 并发派发改为带前置状态的原子条件更新。
7. 为任务收费、积分和执行日志增加数据库级幂等约束。
8. 护理记录改为数据库分页，今日任务消除 N+1 查询。
9. 明确强制生成任务的去重/替换规则，并做真实数据库并发回归。
10. 使用护理员真机完成扫码、弱网、断网恢复、误触和大字体专项验收。
